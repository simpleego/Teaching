# LLM Wiki User가 할일
> LLM Wiki에서 사용자가 해야 할 일은 **문서를 직접 정리하는 것보다, “어떤 지식을 넣고 어떤 기준으로 유지할지 결정하는 것”**에 가깝습니다.

핵심 역할을 흐름대로 정리하면 다음과 같습니다.

### 1. 지식의 범위와 목적 정의

먼저 어떤 Wiki를 만들 것인지 정해야 합니다.

예를 들어:

```text
AI 교육용 Wiki
 ├─ Python
 ├─ Machine Learning
 ├─ Deep Learning
 ├─ LLM
 ├─ RAG
 └─ Agent
```

또는:

```text
회사 기술 Wiki
 ├─ 제품
 ├─ API
 ├─ 개발 가이드
 ├─ 장애 사례
 └─ 운영 매뉴얼
```

LLM이 자동으로 정리할 수는 있지만, **무엇을 지식으로 관리할 것인가는 사람이 결정**해야 합니다.

---

### 2. 원본 자료를 제공하거나 연결

LLM Wiki의 재료가 되는 데이터를 넣습니다.

```text
PDF
DOCX
Markdown
Web Page
GitHub
소스코드
회의록
매뉴얼
논문
FAQ
```

사용자의 역할은 쉽게 말하면:

> "이 자료들을 우리 지식으로 사용해라."

라고 지정하는 것입니다.

그 이후:

```text
문서 읽기
→ 요약
→ 개념 추출
→ 관계 추출
→ Wiki Page 생성
```

은 LLM이 상당 부분 자동화할 수 있습니다.

---

### 3. 초기 구조 또는 분류 기준 설정

완전 자동 생성도 가능하지만, 최소한의 구조를 사람이 정해주는 것이 좋습니다.

예:

```text
AI
 ├─ 기초이론
 ├─ 개발도구
 ├─ LLM
 ├─ RAG
 ├─ Agent
 └─ 프로젝트
```

그다음 LLM이 새 자료를 보고:

```text
LangChain 문서
       ↓
LLM 판단
       ↓
AI / LLM / 개발도구
```

처럼 적절한 위치에 배치할 수 있습니다.

즉 사용자는 **정보 구조(Information Architecture)** 를 설계하고, LLM은 내용을 채우는 방식입니다.

---

### 4. 중요한 지식에 대한 검토와 승인

LLM Wiki에서 가장 중요한 사용자 역할 중 하나입니다.

LLM이 다음과 같이 생성했다고 가정하면:

```text
Transformer
 ├─ Attention
 ├─ Encoder
 ├─ Decoder
 └─ RAG
```

여기에서 `RAG`를 Transformer의 직접 하위 개념으로 넣는 것이 적절한지 사람이 검토해야 할 수 있습니다.

따라서:

```text
LLM 생성
   ↓
User Review
   ↓
Approve / Modify / Reject
```

구조가 필요합니다.

특히 다음 내용은 검토가 중요합니다.

* 중요한 기술 정의
* 회사 내부 규칙
* 법률/의료/금융 정보
* 서로 모순되는 문서
* 오래된 정보
* 출처가 불명확한 정보

---

### 5. 중복·오류·모순을 처리

시간이 지나면 Wiki에는 이런 문제가 생깁니다.

```text
RAG.md
retrieval-augmented-generation.md
rag-system.md
```

실제로는 거의 같은 내용일 수 있습니다.

또는:

```text
문서 A
Python 3.10 사용

문서 B
Python 3.12 사용
```

처럼 정보가 충돌할 수 있습니다.

LLM이 자동으로 발견할 수 있지만 최종 판단은 사용자에게 맡기는 것이 안전합니다.

```text
LLM
 ↓
"중복 가능성이 있습니다."
 ↓
User
 ↓
Merge / Keep / Delete
```

---

### 6. 질문하고 Wiki를 사용

지식이 축적되면 사용자는 일반적인 챗봇처럼 질문합니다.

예:

```text
"RAG와 Fine-tuning의 차이는?"
```

시스템은:

```text
Question
 ↓
Wiki Search
 ↓
관련 Page
 ↓
관계 탐색
 ↓
LLM
 ↓
Answer
```

과정을 수행합니다.

사용자는 검색 방법을 직접 알 필요가 없습니다.

즉:

```text
Keyword Search
Vector Search
Graph Search
```

중 무엇을 사용할지는 시스템 내부에서 처리하도록 만들 수 있습니다.

---

### 7. 좋은 답변을 지식으로 다시 저장할지 결정

LLM Wiki의 중요한 특징입니다.

예를 들어 사용자가 질문합니다.

```text
Q:
RAG와 GraphRAG의 차이는?
```

LLM이 좋은 분석을 생성했습니다.

그 결과가 일회성으로 끝나는 대신:

```text
Answer
 ↓
"Wiki에 추가할 가치가 있는가?"
 ↓
Yes
 ↓
rag-vs-graphrag.md
```

처럼 다시 저장할 수 있습니다.

이때 사용자의 역할은:

> **어떤 답변을 영구 지식으로 남길 것인지 판단하는 것**

입니다.

---

## 따라서 사람이 직접 하지 않아도 되는 일

LLM Wiki의 목적은 다음 작업을 자동화하는 것입니다.

```text
문서 요약
개념 추출
키워드 추출
태그 생성
페이지 생성
관련 문서 찾기
Wiki Link 생성
중복 후보 탐색
내용 업데이트 제안
검색
답변 생성
```

반면 사용자가 담당해야 할 핵심은:

```text
목적 결정
   ↓
자료 선택
   ↓
구조 결정
   ↓
품질 검토
   ↓
중요도 판단
   ↓
최종 승인
```

입니다.

## 기존 RAG 사용자와 비교하면 더 명확합니다

| 역할           | 기존 RAG     | LLM Wiki      |
| ------------ | ---------- | ------------- |
| 문서 업로드       | 필요         | 필요            |
| Chunk 설정     | 개발자가 많이 관여 | 대부분 자동화 가능    |
| Embedding 설정 | 필요         | 선택적           |
| Vector DB 관리 | 중요         | 선택적           |
| Wiki 구조 설계   | 없음         | 중요            |
| 개념 관계 관리     | 거의 없음      | 중요            |
| 생성 지식 검토     | 주로 답변만 검토  | Wiki 자체 검토    |
| 새 지식 저장      | 보통 안 함     | 중요            |
| 기존 지식 갱신     | 원문 재인덱싱    | 기존 Page 수정 가능 |
| 지식 품질 관리     | 상대적으로 적음   | 핵심 사용자 역할     |

가장 중요한 차이는 이것입니다.

```text
RAG 사용자
"어떤 문서를 검색할 수 있게 만들 것인가?"
```

반면:

```text
LLM Wiki 사용자
"어떤 지식을 우리 조직의 지식으로 유지할 것인가?"
```

를 결정합니다.

---

## 결국 LLM Wiki에서 사람의 역할은 '편집장'에 가깝다

기존 Wiki에서는 사람이 직접:

```text
작성
분류
링크
수정
요약
```

을 했습니다.

LLM Wiki에서는:

```text
                 사용자
                   │
        방향 / 기준 / 승인 / 검증
                   │
                   ▼
                  LLM
        ┌──────────┼──────────┐
        ▼          ▼          ▼
       작성       연결       갱신
        │          │          │
        └──────────┼──────────┘
                   ▼
                LLM Wiki
```

가 됩니다.

그래서 사용자 역할을 한 문장으로 표현하면:

> **LLM Wiki에서 사용자는 지식을 직접 작성하는 사람이 아니라, 어떤 지식을 축적하고 유지할지 결정하는 Knowledge Curator 또는 Knowledge Editor 역할을 한다.**

특히 실제 회사나 교육기관에서 사용할 때는 **① 자료 제공 → ② 자동 Wiki 생성 → ③ 사람이 검토 → ④ 승인 → ⑤ 새로운 자료와 질문 결과를 다시 축적**하는 Human-in-the-loop 구조가 가장 현실적입니다.
